# Как декомпилировать

Цикл работы над одной функцией: черновик на C → сборка → сравнение с оригиналом →
правки, пока байты не совпадут.

## 0. Подготовка (один раз)

```sh
make setup
cp /путь/к/диску/SCUS_942.44 disc/
make init        # config/us/splat.yaml, config/us/checksum.sha1
make extract     # asm/us/, src/
make             # должно быть «OK, совпадает с оригиналом»
make expected    # снимок совпадающей сборки, эталон для `make diff`
```

`make init` нужен только при создании проекта. Получившийся
`config/us/splat.yaml` коммитится, и дальше его правят вручную.

## 1. Разделить код на файлы

После первой нарезки весь код лежит одним куском `asm/us/<смещение>.s`.
Оригинальная игра собиралась из многих `.c`-файлов. Их границы видны по
выравниванию функций и по сменам стиля кода; splat подсказывает их сам
(`find_file_boundaries`).

Найдя границу, замените в `config/us/splat.yaml` строку
`[0x..., asm]` на несколько строк. Например (адреса и имена условные):

```yaml
      - [0x1F000, c, gool]      # интерпретатор GOOL
      - [0x24800, c, nsf]       # загрузка страниц NSF
      - [0x29C00, asm]          # дальше пока неизвестно
```

и выполните `make extract`. В `src/gool.c` появятся заготовки:

```c
#include "common.h"

INCLUDE_ASM("asm/us/nonmatchings/gool", func_8002F000);
```

`INCLUDE_ASM` подставляет оригинальный ассемблер, поэтому сборка совпадает
с самого начала. Уже существующие `.c`-файлы splat не перезаписывает.

## 2. Черновик функции

```sh
make decompile FUNC=func_8002F000
```

m2c выдаст черновик на C. Замените им строку `INCLUDE_ASM` для этой функции.
Типы и прототипы m2c берёт из заголовков `include/` (`make ctx` собирает их в `ctx.c`).

Черновик можно доработать на [decomp.me](https://decomp.me): создайте scratch
для PlayStation с компилятором GCC 2.7.2 (PSY-Q). Ассемблер функции возьмите
из `asm/us/nonmatchings/...`, а контекст — из `ctx.c`.

## 3. Довести до совпадения

```sh
make            # собрать и сверить весь исполняемый файл
make diff FUNC=func_8002F000   # сравнение функции с оригиналом построчно
```

`make diff` показывает разницу инструкций и пересобирает при каждом сохранении файла.
Типичные причины расхождений: порядок объявлений переменных, типы (`s16` или `s32`,
`u8` или `s8`), форма циклов (`for` или `while`), временные переменные,
`if` против тернарного оператора.

Если функция не совпадает, но работает правильно, сохраните её так:

```c
#ifdef NON_MATCHING
void func_8002F000(void) {
    /* почти совпадающий C */
}
#else
INCLUDE_ASM("asm/us/nonmatchings/gool", func_8002F000);
#endif
```

`make NON_MATCHING=1` собирает такие функции из C. Это нужно порту, но
контрольная сумма при этом не совпадёт.

## 4. Имена

Понятные имена функций и переменных записываются в `config/us/symbol_addrs.txt`:

```
GOOL_Interpret = 0x8002F000; // type:func
gLevelId = 0x8005A2C0; // size:0x4
```

После `make extract` имена появятся в ассемблере.

## Уточнение параметров компилятора

Первые функции покажут, правильно ли выбраны параметры в `Makefile`:

- `COMPILER` — `gcc-2.7.2-psx` или `gcc-2.8.1-psx`, например `make COMPILER=gcc-2.8.1-psx`;
- `ASPSX_VERSION` — версия ассемблера PSY-Q, влияет на раскрытие макросов
  (таблица различий есть в README maspsx);
- `GP_SIZE` — если игра обращается к глобальным переменным через `$gp`
  (`make init` сообщает `gp_value`), нужен `GP_SIZE=8` и строка
  `include_asm_macro_style: maspsx_hack` в `splat.yaml`.

Правильный набор — тот, при котором простые функции совпадают без ухищрений.

## Библиотеки PSY-Q

Часть кода — это не игра, а библиотеки Sony (libgpu, libgte, libspu, libcd,
libetc, libapi, libc). Их не нужно декомпилировать ради порта: на ПК они
заменяются собственной реализацией. Найденные библиотечные функции стоит
сразу называть (`DrawOTag`, `LoadImage`, `CdRead`, …) и выделять в отдельные
asm-сегменты.

  поэтому эти проекты помогают с именами и структурами.
