# Как декомпилировать

Цикл работы над одной функцией: черновик на C → сборка → сравнение с оригиналом →
правки, пока байты не совпадут.

## 0. Подготовка (один раз)

```sh
make setup
python3 tools/disc_image.py game.cue   # SCUS_942.44 с вашего диска -> disc/
make extract     # asm/us/, src/
make             # должно быть «OK, совпадает с оригиналом»
make expected    # снимок совпадающей сборки, эталон для `make diff`
```

Конфигурация нарезки (`config/us/splat.yaml`) хранится в репозитории, её правят
вручную. `make init` создаёт её заново только для новой версии игры.

## 1. Разделить код на файлы

После первой нарезки весь код лежит одним куском `asm/us/<смещение>.s`.
Оригинальная игра собиралась из многих `.c`-файлов. Их границы видны по
выравниванию функций и по сменам стиля кода; splat подсказывает их сам
(`find_file_boundaries`).

Найдя границу, замените в `config/us/splat.yaml` строку
`[0x..., asm]` на несколько строк. Например (адреса и имена условные):

```yaml
      - [0x1F000, c, gool]      # интерпретатор GOOL
      - [0x24800, c, nsf]       # загрузка страниц NSF
      - [0x29C00, asm]          # дальше пока неизвестно
```

и выполните `make extract`. В `src/gool.c` появятся заготовки:

```c
#include "common.h"

INCLUDE_ASM("asm/us/nonmatchings/gool", func_8002F000);
```

`INCLUDE_ASM` подставляет оригинальный ассемблер, поэтому сборка совпадает
с самого начала. Уже существующие `.c`-файлы splat не перезаписывает.

## 2. Черновик функции

```sh
make decompile FUNC=func_8002F000
```

m2c выдаст черновик на C. Замените им строку `INCLUDE_ASM` для этой функции.
Типы и прототипы m2c берёт из заголовков `include/` (`make ctx` собирает их в `ctx.c`).

Черновик можно доработать на [decomp.me](https://decomp.me): создайте scratch
для PlayStation с компилятором GCC 2.8.1 (PSY-Q). Ассемблер функции возьмите
из `asm/us/nonmatchings/...`, а контекст — из `ctx.c`.

## 3. Довести до совпадения

```sh
make            # собрать и сверить весь исполняемый файл
make diff FUNC=func_8002F000   # сравнение функции с оригиналом построчно
```

`make diff` показывает разницу инструкций и пересобирает при каждом сохранении файла.
Типичные причины расхождений: порядок объявлений переменных, типы (`s16` или `s32`,
`u8` или `s8`), форма циклов (`for` или `while`), временные переменные,
`if` против тернарного оператора.

Если функция не совпадает, но работает правильно, сохраните её так:

```c
#ifdef NON_MATCHING
void func_8002F000(void) {
    /* почти совпадающий C */
}
#else
INCLUDE_ASM("asm/us/nonmatchings/gool", func_8002F000);
#endif
```

`make NON_MATCHING=1` собирает такие функции из C. Это нужно порту, но
контрольная сумма при этом не совпадёт.

## 4. Имена

Понятные имена функций и переменных записываются в `config/us/symbol_addrs.txt`:

```
GOOL_Interpret = 0x8002F000; // type:func
gLevelId = 0x8005A2C0; // size:0x4
```

После `make extract` имена появятся в ассемблере.

## Параметры компилятора

Игра собрана PSY-Q GCC 2.8.1 с `-O2 -G8`. Узнать его можно по тому, что адреса
глобальных массивов и структур загружаются в регистры отдельно (`lui` + `addiu`),
а не подставляются в каждую инструкцию: так делает 2.8.1, а 2.7.2 — нет.
Если какой-то файл не совпадает при явно верном коде, попробуйте другой
`ASPSX_VERSION` (таблица различий есть в README maspsx).

GCC сам вставляет в начало `main()` вызов `__main()`, писать его не нужно.

## Переменные и `$gp`

Ассемблер PSY-Q обращается через `$gp` (`%gp_rel(...)` в asm) только к малым
переменным (до 8 байт), **определённым в том же файле**. К переменной,
объявленной `extern`, обращение всегда идёт по полному адресу (`lui` + `%lo`).

Отсюда правило: если функция читает переменную через `$gp`, эта переменная
определена в том же `.c`-файле. Чтобы такая функция совпала, файл должен
определять переменную, то есть вместе с кодом нужно перенести его `.sdata`/`.sbss`
(в `splat.yaml` это подсегменты `.sdata`/`.sbss` с именем файла). Функции,
которые обращаются к переменным по полному адресу, можно декомпилировать сразу.

## Приёмы, найденные на этом коде

- **Поля вместо отдельных переменных.** Многие «глобальные переменные»
  (`D_80061038`, `D_80061A6C`, …) на самом деле поля больших структур (`ns`,
  `game`, `context`). Если обращаться к ним как к полю (`ns.page_map`), GCC
  расставляет инструкции как в оригинале, а как к отдельной переменной — нет.
- **`goto` вместо цикла.** Если в цикле оригинала константы не вынесены
  за пределы цикла, это, скорее всего, `goto` назад: такой переход оптимизатор
  циклов GCC не видит.
- **Порядок ветвей.** GCC 2.8.1 обычно размещает сразу за проверкой ветку
  `then`. Если в оригинале наоборот, переверните условие.
- **Выражение и `if`.** `return a && b;` и цепочка `if` дают разный код;
  пробуйте оба варианта.
- **`goto` и выбор регистров.** GCC считает обращения к переменной внутри
  `while`/`for` с весом, поэтому переменная из цикла может отобрать регистр
  (`s0`) у другой. Если в оригинале регистры переставлены, попробуйте
  переписать короткий цикл повтора через `goto` (`NSPageUpdate`). Посмотреть,
  как распределены регистры, можно в дампах `cc1 -dg -dl`.
- **Отдельная переменная на каждую роль.** Если один указатель используется
  в двух разных циклах, GCC может добавить лишние `move`. Две переменные
  (`ps` и `next` в `NSUpdate`) убирают их.
- **Лишние `sll`/`sra` на 1.** Пара `sll x,1; sra x,1` — след выражения вида
  `((i + 1) << 1 | 1) >> 1`: в коде вычисляется pgid страницы, а потом из него
  снова её номер.
- **Строки из inline-функций.** Литералы `static inline`-функции попадают
  в `.rodata` там, где функция определена, а не там, где она вызвана. Если
  строки функции лежат в `.rodata` раньше, чем должны по её месту в файле,
  значит, они были во вспомогательной inline-функции выше по файлу
  (`NSPrintRetrySlave`).
- **Примитивы GPU.** Игра берёт примитив из буфера кадра выражением
  `(tail = (T *)tail + 1) - 1` (макрос `GpuAllocPrim` в `include/gfx.h`).
  Если после загрузки `prims_tail` в оригинале есть лишний `move` в другой
  регистр, значит, здесь этот макрос.
- **Константы в начале `.rodata`.** Константа, определённая на уровне файла
  (`const Clut16 D_80010230 = {...}`), попадает в `.rodata` там, где она
  определена. Инициализатор локального массива попадает туда, где стоит
  функция.
- **Два `return` вместо переменной.** `if (a == b) return obj; return NULL;`
  и `res = obj; if (a != b) res = NULL; return res;` дают разный код:
  в первом случае `obj` сразу копируется в `v0`.
- **`i++` в аргументе.** Если в цикле счётчик и указатель увеличиваются до
  вызова функции, в оригинале, скорее всего, `f(&arr[i++])`.
- **Загрузка раньше проверки.** GCC 2.8 планирует инструкции только внутри
  базового блока. Если в оригинале поле читается до ветвления, которое его
  проверяет, значит, в исходнике его прочитали раньше: в переменную или
  выражением через запятую прямо в условии.
- **Общий хвост вместо `else if`.** Если после ветки снова проверяется то же
  условие (`state & 0x8000`), в исходнике идут два отдельных `if`, а не `else if`.
- **Поля структур не путаются со скалярами.** GCC 2.8 считает, что запись в
  поле структуры не может изменить простую глобальную переменную, и
  переставляет загрузки глобальных переменных выше такой записи. Если в
  оригинале каждая загрузка стоит сразу перед своей записью (`lw`, `nop`, `sw`),
  глобальные переменные там были массивами или структурами: `D_8005C244[0]`.
- **Один базовый регистр на два «разных» символа.** Если адрес одной
  глобальной переменной берётся как смещение от адреса другой
  (`lw a0, -0x195C(s0)`, где `s0 = &D_800676B0`), это поля одной большой
  структуры: так нашлось, что `D_800676B0` — поле `D_80065C90.render`.
- **Запятая в индексе.** Повторный вызов, результат которого выброшен
  (`id = (EntityProp(e, 0x9F), EntityProp(e, 0x9F))`), — это макрос оригинала;
  его нужно повторить, иначе пропадёт вызов.
- **Inline-помощник меняет адресацию.** Если три записи идут через
  отдельный регистр-указатель (`addiu v1, s0, 0x384; sw ..., 4(v1)`), в
  оригинале был маленький `static inline` с параметром-указателем
  (`SetVec(game.unk384, x, y, z)`).
- **Тип результата влияет на слоты задержки.** У функции, объявленной как
  `s32`, регистр `v0` считается живым на выходе, и компилятор не кладёт в слот
  задержки инструкцию, которая его портит (видно как лишний `nop`). Если так,
  функция в оригинале была не `void`, даже если ничего не возвращает.
- **Умножение по шагам.** Компилятор сворачивает `x * 3840 * 2` в `x * 7680` с
  другой последовательностью сдвигов. Если в оригинале видно
  `(x << 12) - (x << 8)` и отдельный сдвиг, это было записано сдвигами:
  `(-(d << 8) + (d << 12)) << 1`.
- **Знаковость поля в `switch`.** `slti`/`sltiu` в дереве сравнений `switch`
  показывает, знаковое ли выражение (так нашлось, что `GoolHeader.type` — `s32`).
- **Старшая часть адреса в другом регистре — это поле структуры.** Если
  оригинал грузит глобальную переменную как `lui v0, %hi(x); lw a0, %lo(x)(v0)`,
  а наш C даёт `lui a0; lw a0, ...(a0)`, переменная была полем большой структуры.
  Так нашлось, что `D_80061044` — это `ns.ldat`, `cur_zone` — `D_80065C90.unkCC`,
  а `D_80067A30/34` — поля `D_80065C90` за `render`. Смещение от ближайшего
  известного символа подсказывает, в какую структуру смотреть.
- **Макрос оригинала виден по проверке, свёрнутой константой.** Запись через
  `GoolObjectSetChildren` сразу после `type = 2` даёт другой код, чем прямая
  запись в `children`.
- **Литералы-заглушки.** Пока функция остаётся ассемблером, её строковые
  литералы в `.sdata` нужно объявить в C массивами с теми же именами
  (`char D_800608A8[] = "hrce\n";`), иначе данные съедут.

Неинициализированные глобальные переменные (`.sbss`/`.bss`) объявляются
в C без значения, в порядке адресов. maspsx оставляет их метки в `.sbss`
локальными, поэтому сборка пропускает вывод компилятора через
`tools/comm_globl.py`: он объявляет такие переменные глобальными, как было
в оригинале.

## Библиотеки PSY-Q

Часть кода — это не игра, а библиотеки Sony (libgpu, libgte, libspu, libcd,
libetc, libapi, libc). Их не нужно декомпилировать ради порта: на ПК они
заменяются собственной реализацией. Найденные библиотечные функции стоит
сразу называть (`DrawOTag`, `LoadImage`, `CdRead`, …) и выделять в отдельные
asm-сегменты.
